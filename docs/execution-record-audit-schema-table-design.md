# Execution Record Audit Schema/Table Design

## Purpose

Action 729 designs the future audit schema/table for execution-record audit writer events.

This is a documentation-only schema/table design artifact. It is not schema proof, does not create or apply a migration, does not generate Supabase types, does not implement an audit writer, and does not add any write path.

## Current State

- No audit schema/table exists or is remotely proven for the future audit writer.
- No generated audit table types exist.
- No migration was created or applied by this action.
- No remote environment proof exists.
- No RLS/security proof exists.
- No audit writer exists.
- No audit route/write path exists.
- Dry-run diagnostics exist, but they are not schema proof, migration proof, generated types proof, RLS proof, or write approval.

There is historical draft audit/lifecycle SQL in the repository, including `public.execution_lifecycle_events`, but this design does not treat that draft as the audit writer table and does not claim it exists remotely.

## Proposed Table Identity

- Proposed table name: `execution_record_audit_events`.
- Proposed schema namespace: `public`.
- Purpose: append-only audit events for future execution-record persistence and audit-writer activity.
- Ownership: server-owned persistence/audit subsystem, pending RLS and service-role proof.
- Relation to `execution_records`: each audit row should reference an execution record when a persisted execution record exists.
- Relation to future audit writer: the future writer may target this table only after schema, migration, generated types, RLS/security, server-only, service-role, route/auth, idempotency, duplicate-prevention, and evidence/provenance proof artifacts are complete.

This table identity is proposed, not applied.

## Proposed Indexes And Constraints

Proposed constraints and indexes:

- Primary key on `id`.
- Foreign key from `execution_record_id` to `public.execution_records(id)` if `execution_records.id` is confirmed as UUID and remote schema proof supports it.
- Unique index on `idempotency_key`.
- Unique index on `duplicate_prevention_key` if the duplicate-prevention semantics are table-wide; otherwise a composite unique index using event scope should be designed.
- Index on `execution_record_id`.
- Index on `event_type`.
- Index on `event_status`.
- Index on `created_at desc`.
- Index on `source_fingerprint` if investigation or retry workflows query by source input.
- Check constraint or enum for `event_type` if the event taxonomy is stable.
- Check constraint or enum for `event_status` using an allowlist such as `attempted`, `succeeded`, `failed`, `blocked`, `duplicate`, `unknown`.
- Check constraint for `schema_version > 0`.

Risks if constraints are missing:

- Duplicate audit rows.
- Retry ambiguity.
- Unbounded event/status values.
- Weak forensic queries.
- Orphan rows or false record linkage.
- Silent writer/schema drift.

## Idempotency And Duplicate-Prevention Model

The proposed idempotency key should be derived from stable inputs such as:

- Execution-record identifier when known.
- Event type.
- Event source.
- Source fingerprint.
- Writer schema version.
- Request/attempt scope where appropriate.

The duplicate-prevention key should represent semantic duplication, not merely retry identity. It may include:

- Execution-record identifier.
- Event type.
- Source fingerprint.
- Normalized event payload fingerprint.

Collision handling:

- Exact duplicate idempotency key should return duplicate/no-op semantics in a future writer.
- Duplicate-prevention conflict with materially different payload should block and require manual review.
- Unknown write status must not blindly retry with a new key.
- Manual review is required when collision evidence is ambiguous.

Execution-record id alone is not enough because one execution record may have multiple valid audit events, and the same event may be retried after an unknown network or route status.

## Evidence/Provenance Model

`event_payload` should describe what happened. `evidence_payload` should describe why the audit event is justified and which evidence supports it.

Required provenance concepts:

- Execution-record reference when available.
- Event source and source system.
- Actor type and optional actor id.
- Source fingerprint.
- Timestamp/source clock semantics.
- Request/trace ids.
- Explainable minimized payload.
- No local-only truth as the sole source of authority.
- No broker/Avanza assumptions unless explicitly supported by separate broker/Avanza evidence.
- No credentials, cookies, raw broker pages, raw browser session data, or unrelated PII.
