## Product Intent

Ture remains a day-trading co-pilot for US stocks.

The preferred product direction is semi-automatic first:

- Ture recommends a limited number of trades.
- The user chooses whether to act.
- A semi-auto agent may prepare broker order details.
- The final broker confirmation remains manual and human-confirmed.
- The final `KOP`/`SALJ` click remains outside Ture automation.
- Full automatic execution remains deferred, gated, and unapproved.

Automatic mode is not part of this inventory's implementation scope. Any future
full-auto mode requires a separate high-risk inventory, baseline tests, safety
review, and explicit approval.

## Intended Semi-Auto Flow

1. Ture recommends a trade.
2. User clicks handoff/prepare.
3. Ture creates an execution payload.
4. Agent receives the payload.
5. Agent opens or uses a browser session.
6. Agent fills broker order fields.
7. Agent shows a visible pause/checkpoint at final confirmation.
8. User manually clicks `KOP`/`SALJ`.
9. Agent/Ture captures result/status where safe and approved.
10. Ture records a local or server-safe execution record only where separately
    approved.

This flow prepares order details but does not submit the final order.

## Execution Payload Contract

The semi-auto handoff payload should be explicit, typed, and bounded.

Required fields:

| Field | Purpose |
| --- | --- |
| `ticker` | US stock symbol to prepare. |
| `side` / `action` | `buy` or `sell`; must match recommendation or position state. |
| `quantity` | Integer quantity to prepare. |
| `order_type` | Market, limit, or other explicitly supported type. |
| `limit_market_assumption` | Whether the order expects limit or market handling. |
| `entry` | Planned entry/reference price. |
| `stop` | Required stop-loss level. |
| `target` | Required target level. |
| `risk_per_share` | Entry-to-stop risk per share. |
| `total_planned_risk` | Quantity-adjusted planned risk. |
| `recommendation_id` | Source recommendation identifier, if available. |
| `fingerprint` / `payload_id` | Deterministic handoff identity for duplicate guarding. |
| `expires_at` / `stale_after` | Expiry or staleness timestamp. |
| `account_broker_target_label` | Optional human-readable broker/account target label. |
| `human_confirmation_required` | Must be `true` for semi-auto. |
| `automatic_submit_allowed` | Must be `false` for semi-auto. |

Optional future fields can describe broker-specific display labels, currency,
time-in-force, or route metadata, but they must not grant submit authority.

## Agent Authority Model

- Semi-auto is the default and only approved direction in this inventory.
- Final confirmation is human-only.
- The agent may prepare fields but must not submit.
- `automatic_submit_allowed` is always `false`.
- Sell/exit handoff uses the same human confirmation model.
- Stop-loss/target exits may prepare an order but must not submit it.
- Full-auto requires separate approval and must not be inferred from this
  inventory.

The agent is a preparation assistant, not an execution authority.

## Avanza/Browser Boundaries

- No Avanza API is assumed.
- No Avanza credentials are stored in Ture.
- User logs in manually if needed.
- Agent must not bypass 2FA.
- Agent must not confirm the final order.
- Agent must not modify unrelated account settings.
- Agent must not navigate outside the intended broker/order flow.
- Agent must expose a visible pause/checkpoint before final broker action.
- Agent must surface unknown page state as blocked/unknown, not improvise.
- Agent must never hide final broker risk/confirmation information from the
  user.

## UI Requirements In Ture

Ture should provide a clear handoff experience before any browser-agent work is
considered:

- Handoff preview modal.
- Clear "manual final confirmation" copy.
- Safety checks before prepare.
- Quantity and risk display.
- Stale/expired warning.
- "Broker action not yet executed" copy.
- Prepare status.
- Waiting-for-manual-confirmation status.
- Cancelled/failed/unknown statuses.
- Capture result after user action where safe and approved.
- Pure local/dev-only state-machine review surface remains a next UI step.

The UI must not imply that Ture has submitted or can submit the final broker
order in semi-auto mode.

## Safety Gates

The semi-auto handoff must be blocked unless all required gates pass:

- Recommendation is not stale.
- Market/session is valid.
- Risk per trade is within limit.
- Daily loss limit is not breached.
- Max open positions limit is not breached.
- Stop is present.
- Target is present.
- Quantity is valid.
- Order side matches recommendation or position state.
- Duplicate order guard passes.
- Final confirmation required flag is true.
- Automatic order submission flag is false.

Any failed safety gate should block handoff preparation or downgrade it to a
non-executable preview.

## Capture/Result Model

Possible statuses:

| Status | Meaning |
| --- | --- |
| `prepared` | Payload prepared and ready for agent/browser handoff. |
| `waiting_for_manual_confirmation` | Broker form prepared; user must manually confirm. |
| `user_confirmed` | User reports or capture proves manual confirmation happened. |
| `user_cancelled` | User cancelled or backed out. |
| `broker_rejected` | Broker rejected the action. |
| `unknown` | State could not be classified safely. |
| `failed` | Agent or handoff failed before completion. |
| `timeout` | Handoff/capture timed out. |
| `capture_not_available` | No reliable capture mechanism exists. |

Local storage may currently hold local/dev execution evidence only where
existing client-safe helpers already support it. Server-side writes can happen
only through separately approved server-only paths. This inventory does not
approve client audit writer invocation or new persistence behavior.

- No credentials/env exposure tests.
- UI copy/source-characterization tests.
- Result status mapping tests.

Tests should prove that semi-auto behavior prepares only and never submits.

## Risk Assessment

| Risk | Classification | Notes |
| --- | --- | --- |
| Product UX risk | Medium | Copy must never imply final broker execution is automated. |
| Execution safety risk | High | Wrong side/quantity/price could cause financial loss if submitted manually without review. |
| Broker/account risk | High | Browser automation near broker UI can affect real accounts if boundaries fail. |
| Credential/privacy risk | High | Ture must not store Avanza credentials or bypass 2FA. |
| Regulatory/compliance risk | High | Automation may create advice/execution obligations; full-auto needs separate review. |
| Technical reliability risk | High | Broker DOM/page changes can break automation. |
| Audit/recording risk | Medium | Capture can be ambiguous; unknown states must remain unknown. |

## Current Decision

- Build semi-auto foundation first.
- Do not implement full-auto yet.
- Do not implement real Avanza/browser automation yet.
- Start with payload contract and tests.
