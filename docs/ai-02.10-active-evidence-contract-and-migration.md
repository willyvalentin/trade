# AI-02.10 — additive active-evidence v2 contract and local migration

## Decision

AI-02.10 is the smallest safe response to the AI-02.9 compatibility finding.
It does not modify, reinterpret, migrate or grant access to the existing
`canonical_evaluation_decisions` v1 relation. Instead, it adds a separate v2
migration for `public.canonical_active_evaluation_evidence` and
an I/O-free server-only contract that defines the exact boundary for a future
staging proof.

The v2 relation accepts only complete `visible` or `research_only` evidence
with a 60-minute primary outcome and exactly one 15-minute, 30-minute and
60-minute diagnostic horizon. It stores a distinct active-evidence identity
and idempotency key, requires `inactive_readiness_only=false`, uses
identity/receipt/digest constraints, and is append-only. It has RLS enabled
and forced, no policies and no application-role grants. The migration has
passed only the disposable local PostgreSQL proof described below; it is not
applied to staging, production or any shared database by this work.

## Authority boundary

The TypeScript contract is server-only and I/O-free. It validates only an
immutable plan that preserves v1, selects the new v2 relation and insists on a
separately authorized real server-owned completed bundle. A valid result is
`active_evidence_contract_validated_not_authorized_not_executed`.

It does not authorize or execute a database operation, does not apply the
migration, does not bind a source, does not access staging or production, and
does not read a secret or payload. It creates no evaluator, offline dataset,
promotion, writer/runtime, provider/model, deployment, broker or production
authority.

## Why this shape

Changing v1 would retroactively change the meaning of the historical
`historical_synthetic` receipt. A new relation makes the active/evaluable
semantics explicit, keeps existing provenance valid, and keeps a later writer
permission as a distinct authorization rather than an accidental side effect
of schema creation.

The source condition intentionally remains unresolved. `ture-staging` had no
completed `recommendation_outcomes` rows on the AI-02.8 preflight, so neither a
fixture, the historical receipt nor the private legacy-preservation relation
may populate v2. The contract prevents those shortcuts while the genuine
server-owned producer is selected separately.

## Verification and next gate

The provider-free test covers exact scope, v1 preservation, false-active
readiness, fixture/legacy rejection, malformed-object rejection, migration
containment, append-only behavior and registration in the unchanged six-shard
suite. `scripts/ai-02.10-local-postgres-matrix.mjs` is the reproducible
disposable PostgreSQL acceptance matrix: it creates a v1 sentinel, applies the
new migration locally, verifies RLS/ACL/append-only/rollback behavior and
proves that the sentinel is unchanged. On 2026-09-06 it passed all seven
scenarios against a disposable local Docker PostgreSQL container: migration
application, v1 preservation, default-deny RLS/ACLs, owner-only valid insert,
invalid-row rejection, append-only mutation rejection and rollback leaving no
row. The run contacted no external database, staging or production. Any
application to staging remains a separate request.

After that local database proof, the remaining prerequisite is a separately
authorized binding to one real server-owned completed recommendation-and-
outcome bundle. Only then can an explicit staging-only migration application,
identity/digest preflight, one bounded insert, containment and independent
minimal readback be considered. None of those steps is implied by AI-02.10.
