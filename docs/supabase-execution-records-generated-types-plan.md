# Supabase Execution Records Generated Types Plan

## 1. Purpose

This document defines a safe future plan for generating and verifying Supabase
execution-record table types.

The plan covers current known state, preconditions, generated type destination,
future/manual generation steps, type verification, drift handling, integration
gates, no-write verification, risks, and recommended next action.

This plan is documentation-only. It does not apply migrations, modify Supabase
schema, generate types, edit generated type files, enable production writes,
create execution records, modify insert routes, change persistence behavior,
write Supabase/localStorage, append audit records, update stats/PnL, roll
back/correct records, mutate trades, wire UI, touch Avanza/browser behavior, or
change broker/order behavior.

## 3. Preconditions Before Type Generation

Before generating execution-record Supabase types later, confirm:

- The execution-records migration is applied to the intended target
  environment.
- The target Supabase project/environment is verified.
- The target branch/environment is known.
- Schema inspection after migration confirms `public.execution_records`.
- RLS/security expectations are reviewed and documented.
- Generated types destination is decided.
- Type generation command and required environment variables are decided.
- The repo is clean enough to review generated diffs.
- Production writes remain disabled.
- Insert route remains dry-run-only unless a separate approved action changes
  it.
- No candidate builder or persistence runtime code depends on generated types
  before those types are reviewed.

Do not generate types from an unverified project or a database where the
execution-records migration application status is unknown.

## 4. Generated Types Destination

Current convention status:

- Repository inspection did not find an established generated Supabase database
  type file for `public.execution_records`.
- No file such as `database.types.ts`, `supabase.types.ts`,
  `types/supabase`, or `supabase/types` was identified as the current
  generated DB type destination.

Preferred approach:

- Confirm the project convention before generating.
- If a generated database types file already exists in the target branch, use
  that location.
- If no convention exists, choose a single explicit destination in a separate
  action before generating.

Fallback proposed location if no convention exists:

- `lib/supabase-database.types.ts`

Naming conventions:

- Use a name that clearly indicates generated database types.
- Avoid mixing generated table types with handwritten app contracts.
- Keep generated types separate from `ExecutionRecordCandidate`,
  `ExecutionRecordPersistenceInput`, bridge contracts, and validator contracts.

Import strategy:

- Runtime code should import generated types only after migration application
  and generated type review are complete.
- Prefer type-only imports where possible.
- Generated types should not replace validation contracts.
- Generated types should support persistence mapping, not bypass validators.

Commit policy:

- Generated type files may be committed only after the target project and
  schema are verified.
- Commit generated types separately from runtime write enablement when
  possible.
- Do not commit stale generated types from a different Supabase project.

## 5. Future Type Generation Steps

These steps are a future/manual checklist. They were not executed by Action
551.

1. Verify Supabase project/environment.

- Confirm project ref, URL, branch/environment, and local/staging/prod target.
- Confirm credentials and CLI context point to the intended project.

2. Verify migration application.

- Confirm `public.execution_records` exists in the target DB.
- Confirm columns, constraints, indexes, comments, and RLS/policies.

3. Run type generation command.

- Use the approved project command or Supabase CLI workflow.
- Generate against the verified target database only.
- Write output to the agreed generated type destination.

4. Inspect generated diff.

- Confirm only expected generated type output changed.
- Confirm no runtime code or route behavior changed.

5. Confirm execution-record table types exist.

- Verify generated types include `public.execution_records`.
- Verify insert/update/select row shapes if the generator emits them.

6. Confirm related enums/JSON fields.

- Confirm check-constrained text fields are represented as strings unless
  manually typed elsewhere.
- Confirm JSON fields are represented safely.

7. Run validation.

- Run `./node_modules/.bin/tsc --noEmit`.
- Run `npm run lint`.
- Run relevant e2e or contract tests where environment allows.

8. Update docs/checkpoint/QA notes.

- Record target project/environment, generation command, output file, and
  validation results.

9. Keep writes disabled.

- Do not enable production writes in the generated-types action.
- Keep insert route dry-run-only unless a separate approved write-boundary
  action changes it.

## 7. Drift Handling

If generated types do not include `execution_records`:

- Stop before runtime integration.
- Confirm the migration was applied to the target database.
- Confirm the generation command points to the intended project.
- Confirm the output file is the expected generated type destination.

If generated columns differ from migration docs:

- Identify whether the database, migration file, or docs are stale.
- Update the stale artifact in a separate reviewed action.
- Do not patch runtime code around unexplained drift.

If nullable/required semantics drift:

- Recheck migration nullability and defaults.
- Recheck generated insert/update/select type conventions.
- Update contracts or migration only after a schema review.

If contracts expect fields absent from schema:

- Decide whether the field belongs in schema, metadata, audit metadata, or a
  separate table.
- Update contracts, migration, or docs in a separate action.

If schema has fields not modeled by contracts:

- Decide whether contracts should expose them, validators should ignore them,
  or docs should mark them as reserved.

When to update contracts vs migration vs docs:

- Update docs when the mismatch is explanatory or planning-only.
- Update contracts when app-level validation needs the field.
- Update migration when the database shape is wrong or incomplete.
- Do not update generated types manually.

## 10. Risks

Generated types from wrong project:

- Types could reflect a different database or branch.

Stale generated types:

- Runtime code could compile against types that no longer match the target DB.

Migration not applied but types assumed valid:

- Generated type presence does not prove target environment readiness.

Schema/contract drift:

- Contracts, migration, generated types, and route mapping can diverge.

Nullable mismatch:

- Insert code could omit required fields or mishandle nullable fields.

JSON field misuse:

- Metadata/audit JSON can become an untyped dumping ground without validators.

RLS/security mismatch:

- Generated types do not encode security policy or ownership checks.

Production write path opened too early:

- Types could create false confidence before persistence gates are complete.

Client/server boundary confusion:

- Direct client writes must not be inferred from generated type availability.
